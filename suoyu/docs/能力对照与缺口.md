## 二、信息搜集「打偏」的修法与现状

**症状**：给企业名，回来的域名是 `ces.cn`、`roboind.com`、`360.cn`、`zj.gov.cn`、`zjol.com.cn` 这类无关域。

**根因链（逐条修掉的）**：

1. 查询词由企业名机械拼接，带行业词、半截品牌词 → 引擎把同行业公司一起召回。
2. 拼音域名猜测霸榜：`_brand` 没剥行业词，「XX科技」直接拼成 `xxkeji.com` 参与打分。
3. ICP 反查恒空（接口字段解析错），少了一路最强归属证据。
4. 平台根域误判：`kuaishou.com` 在平台名单里，自家品牌被 −60 打成 rejected。
5. 短品牌误命中：两字中文品牌用子串匹配，`xunmengvip.com` 被认成本主体。
6. **引擎降级**：Bing 对多字中文长查询退化成「只查开头几个字」，回来的全是字典站、地域门户、同字开头的别家。
7. **只打一个查询词**：`domain_evidence()` 写死 `engines=("bing",)`，而官网域常常只出现在「品牌 + 官网」这一条结果里 → 改投前 3 个查询词、引擎用 `pick_engines()` 实测挑。
8. **「这个词 0 条」被当成引擎失效**：360 对长尾词常见 0 条、对裸品牌稳定出十几条，被踢出后整轮只剩降级的 bing → `pick_engines` 只剔「降级」引擎。
9. **仿冒 / 加盟站**：页面满屏品牌名、自称官网，但页脚版权属于另一家公司，或通篇「加盟 / 招商 / 开店咨询」。原打分靠「自称官网 + 标题含品牌」就能拿 115 分 → 新增 `W_FOREIGN_SUBJECT` 反向证据（−60）与 `_is_franchise_page()`。
10. **根域无 A 记录**：官网只挂 `www`（`moutaichina.com`）被活域闸误杀。

**现在的判据（`enterprise.py`）**：

| 证据 | 权重 | 说明 |
|------|------|------|
| 站内自我声明 | +40 | 企业名与备案号 / 版权 / 关于我们同段 |
| 站点自报主体 | +40 | 页脚 / 标题写的就是这家 |
| 站点标题含品牌 | +35 | 需与域名 / 声明交叉 |
| ICP 备案主体 | +10 | 命中即强证据 |
| 搜索标题 / 摘要 | +25 / +15 | 前 4 位才算 |
| 多引擎同时出现 | +10 | 跨引擎一致性 |
| 证书 SAN | +10 | 辅助 |
| 公共主体后缀 | −50 | `gov.cn` / `edu.cn` |
| 平台根域 | −60 | 地图 / 黄页 / 招聘 / 媒体 |
| **站点自报他方主体** | **−60** | 仿冒 / 加盟站形态 |
| 排位偏远 / 只被提及 | −10 / −5 | |

- 强证据（自报主体 / 站内声明 / 域名即品牌 / ICP）才可能过 45 分的确认线；弱证据封顶 44 落 `pending`。
- 站点自报主体与目标无关时**直接降 pending**，不靠扣分（页面文案可伪造，扣分能靠别的路补回来）。
- **pending / rejected 一律不进 pipeline**，只在 UI 的「域名归属证据」表展示，附每路分数明细。
- 两字中文品牌必须自报主体或 ICP 命中才算确认。

**回归结果（`collect_entity`，2026-11-08 复测）**：

```
瑞幸咖啡           113s  domains=[lkcoffee.com]                    （改前 3 个，含 2 个加盟站）
浙江东方金融控股集团 96s  domains=[]                                （全部候选正确淘汰）
招商银行                 domains=[cmbchina.cn, cmbchina.com]
贵州茅台                 domains=[moutai.com.cn]
阿里巴巴集团             domains=[alibabagroup.com]
```

- 瑞幸的 `bjcltea.cn` / `meizuotea.cn`（盗用品牌做招商）从 confirmed 降到 pending 40 分。
- 浙江东方返回空域属于**正确结果**：该主体没有可信自有官网（`e-dfjr.com` 版权方是上海商弛，判 rejected；`zjdfjr.cn` 等 NXDOMAIN）。
- 引擎侧已到顶：360 对该企业「官方网站 / 官网 / 网址」三种查询全部 0 条，bing 对家宽出口全程降级。
- **剩下的缺口是「企业名 → 域名」的权威数据源**，见 §2.1。

### 2.1 ICP 反查的现实约束（2026-11-08 复测 11 家入口）

| 入口 | 结果 |
|------|------|
| `icp.chinaz.com/{企业名}` | 200，但正文永远「暂无数据」，数据走需要登录/付费的异步接口 |
| `icp.aizhan.com` | 页面 200，正文空（异步 + 验证码） |
| `boce.com` / `beian88` / `beianx` / `sojson` / `icp.xiexie` / `xinyong` / `tool.lu` | 404 / 410 / DNS 已停 |
| `beian.miit.gov.cn` | 521 + 加速乐，API 401/500 |
| 天眼查 / 企查查 / 爱企查 | 419 / 需登录 / 需 JS 渲染，REST 不可用 |

结论：**公开网页渠道没有「企业名 → 备案域」的稳定入口，要走官方备案查询接口。** 现在 `icp_by_company()` 的主路是内置的 MIIT 备案查询（自取令牌 + 几何滑块求解 + 精确主体名翻页，带 7 天落库缓存与频控熔断），另有 aizhan 兜底；都被挡时由搜索 + 拼音猜测 + AI 复核继续跑，不断链，并在结果里说明卡在哪一步。

**不依赖任何本机外部服务或外部可执行程序，也不要求配置大模型 key。** 要再补强这条路，只有两条：用户自备企查查 / 天眼查 key、或走商业 API。两条都不进默认链路。

## 三、还缺什么、怎么补

### 3.1 TCP 服务嗅探（sniffer：24 / 28）

**已有 24 组**（`probe.TCP_PROBES`）：Redis、Memcached、ZooKeeper、MongoDB、JDWP、Dubbo、AJP、SSH、FTP、RDP、Rsync、RMI、T3(WebLogic)、SMB、NFS、PostgreSQL、SMTP、POP3、IMAP、CobaltStrike、Oracle TNS、SOCKS4/5、ZMTP、IIOP·Hadoop IPC。

**还缺 4 类**：LDAP（389/636）、HRPC、ProxyHTTPS（CONNECT 代理嗅探）、以及 RDP 的细粒度协商（现在只到 TPKT 层）。

- 补法：往 `TCP_PROBES` 加一项 + 一个 `_p_*` 判定函数即可，骨架已经是「端口集合 → 判定」表。
- 单站性能：`deep` 阶段走 `http_probes(only=WEB_FALLBACK)`，7 组 / 55 请求并发，单站约 17.5 秒。

### 3.2 口令（brute：18 / 28）

**已有 HTTP 14 类**（`credential.CRED_TARGETS`）：ActiveMQ、APISIX、Druid、Grafana、Harbor、Jenkins、Nacos、Nexus、Openfire、Tomcat。
**已有 TCP 4 类**（走原生协议，不依赖客户端库）：MySQL、PostgreSQL、MongoDB、Redis。

**还缺 10 类**：SSH、FTP、IMAP、POP3、SMTP、RDP、SQLServer、Exchange、Gitlab、ManageIQ、Clickhouse、Shiro CBC/GCM。

- **设计取舍：本工具不做字典遍历。** 只在用户自己放了 `credential_lists/<组件>.txt` 时才逐条验证，无文件整段跳过。
- 高价值可补：SSH（`paramiko` 或原生 `userauth`）、SQLServer（TDS 登录包）、Gitlab / Clickhouse（HTTP 表单验证，成本最低）。

### 3.3 单点 PoC（poc：0 / 5）

xing 有 5 条：Django Debug、GitLab 用户名泄露、UEditor SSRF、UEditor 存储 XSS、WEB-INF/web.xml 泄露。

- 值得单独移植的是 **Django DEBUG 页**（配置全泄）、**UEditor SSRF**（回显型）、**WEB-INF/web.xml 泄露**（读得到就有源码线索）。
- UEditor 存储 XSS 只对自己有影响，优先级低；GitLab 用户名泄露交给 nuclei。

### 3.3.1 反向监听（listener：3 / 3 已对齐）

xing 的 listener 是带外回显基础设施：DNS 监听、HTTP API 回调，plus 查询命中记录。索舆原来 SSRF / RCE 探测只能看同步回包，盲打能力为零。

现在在 `arlx/engine/listener.py`，零新依赖：

| 能力 | 实现 |
|------|------|
| 带外 DNS | UDP+TCP 53，`dnspython` 解析报文，`{token}.{自定义域}` 的任意查询都记一条命中，回 `A 127.0.0.1` |
| 带外 HTTP | 回调口（默认 8913）记方法 / 路径 / 头 / 体 / 来源 IP，任意路径都收 |
| 查看命中 | `GET /api/listener/hits` + 前端「带外回显」页，可按任务 / token 过滤 |

- 每任务一个一次性 token：`listener.alloc(task_id)` → `dns_name`（`{token}.{listener.domain}`）与 `http_url`（`http://{出口IP}:{port}/{token}`）。
- 需要用户自备一个可解析的域名做 NS 委派，没有域名时 DNS 段自动关闭，HTTP 回调仍可用（公网可直连本机时）。
- 与 xing 的差别：xing 的 `/weblogic/<payload>`、`/eureka/<payload>` 会在回调服务里拼 RCE XML 木马并执行；索舆只保留「记录回连」的检测能力，不内置 exploit 模板。


### 3.4 字典

缺 `port_*.txt`、`password_*` / `username_*` 28 套、`domain_top300.txt`、`noscreenshot.jpg`。内部字典（子域 2w、目录 200、文件 200）已有；外部项目的爆破字典按 §3.2 的取舍**不需要**跟。

### 3.5 其它

| 项 | 状态 | 说明 |
|----|------|------|
| Shiro 密钥反序列化 | 缺 | 识别能认出 Shiro；拿到 `rememberMe` 后跑 CBC/GCM 解密需自研 gadget，成本高 |
| Nacos / WebLogic 认证绕过链 | 缺 | 识别 + 未授权探针已覆盖「能不能进」；利用链交给 nuclei |
| 资产变化监控 | 缺 | 探微有 `asset_site_monitor`；索舆有周期任务 + 新资产推送，可覆盖大部分场景 |

## 四、AI 是怎么放的

**原则：没有 AI 也完整可跑，AI 只加分。**

| 阶段 | 无 key 时 | 有 key 时 |
|------|-----------|-----------|
| 企业名 → 域名 | 规则 + 证据加权打分 | 只对 pending 段复核归属，调状态不改候选集 |
| 一个域都没有 | 返回空 + 备注 | `guess_domains()` 猜域，猜出来仍要过打分闸 |
| 关键词扩展 | 关闭 | `deep.ai_search` 打开后扩展检索词 |
| 任务结束研判 | 按规则排序 + 计数摘要 | `deep.ai_triage` 按风险重排并写结论段 |
| 小程序 / App 归属 | 包名域名 + 证书 SAN + SDK 名单 | 从应用描述里抽主体别名 |

- 开关在 `config.yaml`：`sources.deepseek` / `sources.openai` 留空即无 AI。
- AI 输出**不进归属确认回路**：确认只看强证据，防止模型幻觉把无关域放进来。
- 所有 AI 调用都包在 `try/except` 里，抛异常 = 维持规则结果，不影响任务状态机。

## 六、微信小程序 / App 采集

### 6.1 微信小程序（`applet.py`）

| 入口 | 能做到 | 边界 |
|------|--------|------|
| AppID（`wx` + 16 位 hex） | 查主体、域名、证据 | 需要先有 AppID |
| 结果里明文 AppID / 分享链 | 反查主体与域名 | 依赖检索命中 |
| 企业名 / 域名 | **不做**按小程序名检索 | 企业名输入直接走归属分支 |

**实测结论：免费公开渠道拿不到「名称 → AppID」。** `mp.weixin.qq.com/wxawap/...`、`wxawap/wap/search`、`cgi-bin/wxaapp_getqrcode`、`cli-api.weixin.qq.com`、`xcx.qq.com` 全部 404/不可用；搜狗微信只出文章；各应用市场无小程序条目。

现实链路只有两条：**已知 AppID 反查**，或**搜索结果里明文出现的 AppID / 微信分享链**。要补「名称 → AppID」需用户自备开放平台凭证或第三方收费库，不进主流程。

### 6.2 App（`mobile.py`）

| 链路 | 来源 | 免费 | 说明 |
|------|------|------|------|
| 名称 → Android 包名 | 应用宝 `sj.qq.com/search?q=`（SSR `__NEXT_DATA__`，`pkg_name` + `name` 成对） | 是 | 直连可用，不需要 key |
| 名称 → 包名兜底 | 移动搜狗 / 360 | 是 | 结果块里 `data-packagename` 给包名 |
| 包名 → 域名 / SDK / 证书 | 应用宝详情页、APK 反查 | 是 | 只回市场详情形态的线索 |
| 开发者 → 其他 App | 详情页 `developer` → `collect_entity` | 是 | 只收 `confirmed` 主体 |

- **反爬注意**：搜狗 / 360 封出口 IP。连打十几次整段 antispider，换 UA 无效，只能换出口（`proxy.sources_via_proxy`）。
- `search.py` 因此有同引擎串行 + 2.5s 间隔 + 10 分钟缓存。
- iOS 侧只有 `apps.apple.com` 检索线索，拿不到包内容（IPA 加密），信息量低于 Android。
- 基线耗时：招商银行 59.3s、瑞幸咖啡 70.7s（含开发者扩线）。

### 6.3 备案反查（`passive.py` 的 `src_miit`）

工信部备案把「主体名」和四类载体绑在一起，是绕开搜索噪声拿到**真实自有域名**最硬的证据源。xing 在 `osint_service/ymicp.py` 里做过，索舆按同样四类补齐：

| 载体 | 参数 | 返回里最有用的字段 |
|------|------|--------------------|
| 网站 | `sp=0`，按 `domainName` 精确查 | `unitName`、`serviceLicence` |
| App | `sp=1` | `serviceName`、`serviceLicence`、`version` |
| 小程序 | `sp=2` | 同上，能直接拿到小程序备案号 |
| 快应用 | `sp=3` | 同上 |

- 接口 `https://beian.miit.gov.cn/api/...` 只有 Referer/Origin 校验，没有 sign；偶发风控返回「工信部服务器异常」，重试一次即可。
- **用途一**：给企业名找网站备案域，替代 `icp_by_company()` 那些已失效的免费入口。
- **用途二**：给小程序补 AppID —— 备案列表里 App 名是中文名，但小程序备案号 + 名称对得上时，能反过来确认「这个主体确实有这个小程序」，再把名称拿去 `/api/applet/search`。
- 只在配置里开了 `sources.miit` 或直接调用时才打，不快照。

### 6.4 引擎归组

`search.ENGINES`：`bing` / `baidu` / `sogou` / `360` / `ddg` / `baidu_m` / `so360_m` / `sogou_m` / `yyb`。

- `DEFAULT_ENGINES = ("360", "bing", "sogou")`：国内裸请求只有这三个能稳定出数。
- 实测 360 对裸品牌最稳，对「品牌 + 官网」长尾词常 0 条；bing 对家宽出口长期降级，由 `_is_degraded` 拦。
- 移动页 + 手机 UA 是绕过 PC 页验证码的稳定路线。
